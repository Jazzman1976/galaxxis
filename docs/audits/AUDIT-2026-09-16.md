# Galaxxis — Code-Audit

**Stand:** 2026-09-16 · **Branch:** `develop` · **Letzter Commit:** `64e6f7a` (2026-02-08)

Vollständige Durchsicht von `Galaxxis.Core`, `Galaxxis.Data` und `Galaxxis.Web`.
Ersetzt das Audit vom 2026-09-13; seitdem wurde nichts committet, aber die Durchsicht war diesmal
tiefer und hat den Befund zur `HomeController`-Zugriffskontrolle sowie den `NewPlayer/Spawn`-Exploit
neu aufgedeckt. Ein damaliger Befund war veraltet und ist korrigiert (siehe Ende).

Einordnung vorweg: Das ist ein Einzelentwickler-Hobbyprojekt in frühem Zustand ohne öffentliches
Deployment. Die Sicherheitsbefunde sind entsprechend nicht „Produktionsvorfall", sondern das, was
vor einem ersten echten Multiplayer-Betrieb abgearbeitet sein muss. Mehrere hartcodierte Werte sind
bewusste Fresh-Install-Hilfen und keine vergessenen Debug-Reste.

## A. Zugriffskontrolle — höchste Priorität

### A1. `HomeController`: keine einzige Besitzprüfung

> **Einordnung:** `Home` ist Alt-Gerüst aus der frühesten Entwicklungsphase — eine Seite, die
> sämtliche Logik gleichzeitig sichtbar machen sollte — und soll komplett entfallen. Der Zielzustand
> ist **Löschen, nicht Härten**; siehe „Der schnellste Weg durch A1/A2" weiter unten. Bis dahin sind
> die Endpunkte allerdings live (siehe A1b), die folgende Beschreibung gilt also für den Ist-Stand.

`Views/Home/HomeController.cs` — jede der ~20 POST-Actions nimmt `planetId` direkt aus dem Request
und ruft `PlanetProvider.GetPlanet(planetId, true)` auf, ohne zu prüfen, ob der Planet dem
angemeldeten Spieler gehört.

```csharp
[HttpPost]
public IActionResult BuildOreMine(int planetId)
{
    Models.Planet planet = PlanetProvider.GetPlanet(planetId, true);   // ← keine Prüfung
    planet.GetOreMine().Build(out string info);
```

Jeder angemeldete Spieler kann damit auf **jedem Planeten im Universum** bauen, die Auslastung
verstellen und Schiffe/Verteidigung produzieren — auf Kosten der Ressourcen des fremden Planeten.

`Attack` und `Scan` sind schlimmer: sie nehmen zusätzlich `userId` aus dem Request und laden damit
die Flotte eines **beliebigen anderen Spielers**:

```csharp
public IActionResult Attack(int planetId, int userId, int planetIdTarget)
{
    User user = UserProvider.GetUser(userId, true);                    // ← Fremd-User frei wählbar
    List<Ship> planetShips = user.Ship.Where(...).ToList();
```

Damit lässt sich die Flotte eines Fremden gegen ein beliebiges Ziel schicken.

**Fix:** Ersatzlos entfernen (bevorzugt, siehe unten). Falls `Home` als Entwickler-Übersicht noch
eine Weile gebraucht wird: Besitzprüfung zentralisieren statt sie 20× zu wiederholen — Action-Filter
oder eine Hilfsmethode `GetOwnedPlanetOrForbid(planetId)` auf einer gemeinsamen Controller-Basis.
`userId` grundsätzlich aus `ICurrentUserService` beziehen, nie aus dem Request.

### A1b. `Home` ist trotz Alt-Status noch von jeder Seite erreichbar

Die reguläre Spielkette ab Login geht über `Start` → `Universe` → `Galaxy` → `GalaxxisSystem` →
`Planet` → Gebäude-Controller. `Home` liegt nicht darin. Erreichbar ist es trotzdem über drei
Stellen:

| Ort | Verweis |
| --- | --- |
| `Views/Shared/_Layout.cshtml:17` | Header-Link „Home" für **jeden** angemeldeten Nutzer, auf jeder Seite |
| `Views/NewPlayer/NewPlayer.cshtml:30` | `<a href="/home">go to home</a>` |
| `Views/Account/AccountController.cs:77` | `Logout` leitet nach `Home` um — das ist `[Authorize]`, also direkt weiter zum Login |

Unabhängig davon bleiben die Routen erreichbar, solange der Controller existiert: Verlinkung
entfernen genügt nicht, die Actions sind weiter per URL ansprechbar. Der Header-Link ist aber der
Grund, warum A1 heute nicht nur theoretisch offen ist.

Nebenbefund: Der `Logout`-Redirect auf eine `[Authorize]`-Seite ist ein Umweg über den
Login-Redirect. Ziel sollte `Start` sein.

### A2. `HomeController`: kein CSRF-Schutz

Keine der POST-Actions in `HomeController` trägt `[ValidateAntiForgeryToken]` (die neueren
Gebäude-Controller tun es). Die Razor-Formulare senden zwar ein Token mit, serverseitig wird es
nicht geprüft. Zusammen mit A1 heißt das: eine präparierte fremde Seite kann im Namen eines
eingeloggten Spielers beliebige Aktionen auf beliebigen Planeten auslösen.

**Fix:** Global per `services.AddControllersWithViews(o => o.Filters.Add(new AutoValidateAntiforgeryTokenAttribute()))`
absichern, statt Attribut für Attribut.

### A3. `NewPlayer/Spawn`: unbegrenzt Planeten abgreifen

`Views/NewPlayer/NewPlayerController.cs:32` — `Spawn` weist dem Aufrufer einen zufälligen freien
Planeten zu, ohne zu prüfen, ob er schon einen hat:

```csharp
public IActionResult Spawn(NewPlayerViewModel model)
{
    Models.Planet randomPlanet = PlanetProvider.FindRandomNobodyPlanetInUniverse(model.UniverseId);
    User user = _currentUserService.GetGalaxxisUserAsync()...;
    model.HasAnyPlanet = PlanetProvider.AssignPlanetToUser(randomPlanet.PlanetId, user.UserId);
```

`HasAnyPlanet` wird nur zur Anzeige gesetzt, nicht als Bedingung ausgewertet. Die Action ist per GET
erreichbar, ohne `[HttpPost]`, ohne Antiforgery-Token. Wiederholtes Aufrufen von
`/newplayer/spawn?universeId=1` sammelt beliebig viele Planeten ein.

**Fix:** `[HttpPost]` + Antiforgery, und die Zuweisung an die Bedingung „Spieler hat noch keinen
Planeten" knüpfen. Passt zum dokumentierten Onboarding-Ziel (Planet erst beim Betreten des
Universums, aber genau einmal).

### A4. `NewPlayerController` ohne `[Authorize]`

Derselbe Controller trägt kein `[Authorize]`. Anonyme Zugriffe kommen nicht wirklich durch, aber aus
dem falschen Grund: `GetGalaxxisUserAsync()` liefert `null` und `user.UserId` wirft dann eine
`NullReferenceException` → HTTP 500 statt Redirect zum Login.

### A5. `AdminController`: jeder eingeloggte Spieler ist Admin

`Views/Admin/AdminController.cs` hat nur `[Authorize]`, keine Rollenprüfung — und
`Views/Shared/_Layout.cshtml:24` blendet den Admin-Link für **jeden** authentifizierten Nutzer ein.
Die einzige Admin-Funktion ist das Starten/Stoppen des Tickers, also der Uhr des gesamten
Universums. Ein beliebiger Spieler kann das Spiel für alle anhalten.

**Fix:** Rolle einführen (`[Authorize(Roles = "Admin")]`) und den Layout-Link entsprechend
konditionieren. Die Rollenverwaltung ist über `AppRole` bereits vorhanden, aber ungenutzt.

### A6. `Account/AddAdmin` ist öffentlich erreichbar

`Views/Account/AccountController.cs:152` — der Controller trägt kein `[Authorize]`, `AddAdmin` ist
per GET von außen aufrufbar, legt das Administrator-Konto an und zeigt anschließend Benutzername
**und Passwort** im View an:

```csharp
IdentityResult result = await UserMgr.CreateAsync(user, "***REMOVED***");
ViewBag.Message = "Admin user was created. UserName: Administrator, Password: ***REMOVED***";
```

Bei bestehendem Admin passiert nichts Schlimmes, aber auf einer frischen Instanz nimmt der erste
Besucher das Admin-Konto in Besitz.

**Fix:** Dieser Bootstrap-Schritt gehört nicht in einen Web-Endpunkt. Passender Ort ist die
`Galaxxis.Data`-Konsole, die bereits ein `CreateAdmin` hat — dort mit Zugangsdaten aus der
Konfiguration statt aus Literalen.

### A7. Login: GET-Bindung, kein Lockout, kein Token

`AccountController.Login` (Zeile 43) ist nicht auf `[HttpPost]` beschränkt und bindet
`LoginViewModel` auch aus der Query-String — Zugangsdaten können in Browser-History, Proxy- und
Serverlogs landen. Zusätzlich:

- kein `[ValidateAntiForgeryToken]`
- `PasswordSignInAsync(model.User, model.Password, true, false)` — letzter Parameter
  `lockoutOnFailure: false`, also unbegrenzte Rateversuche
- `isPersistent: true` fest verdrahtet, ohne „angemeldet bleiben"-Auswahl

Gleiches Muster bei `Register` und `SelectUniverse`.

### A8. Gebäude-Controller: 500 statt 403

`Views/OreMine/OreMineViewModel.cs:18` (und identisch in `CrystalMine`, `Factory`,
`NeutronAccelerator`, `PowerSupply`) durchsucht `user.Planet` nach der angefragten `planetId` und
lässt `Planet` schlicht `null`, wenn nichts passt:

```csharp
foreach (Data.Models.Planet p in user.Planet)
    if (p.PlanetId == planetId) { this.Planet = p; break; }
// kein else → Planet bleibt null
```

`OreMineController.BuildOreMine` ruft danach ungeschützt `model.Planet.GetOreMine(true)` auf →
`NullReferenceException`. Die Zugriffskontrolle greift also inhaltlich korrekt, meldet das Ergebnis
aber als Serverfehler statt als 403/404.

Positiv: Diese Controller sind das gute Gegenbeispiel zu A1 — `[Authorize]`,
`[ValidateAntiForgeryToken]` und Planet-Scoping über den Benutzer sind vorhanden.

## B. Secrets und Repository-Hygiene

### B1. Zugangsdaten im Git-Verlauf

| Ort | Inhalt |
| --- | --- |
| `Galaxxis.Web/appsettings.json:3` | `Server=WALL-E;…;Password=***REMOVED***` |
| `Galaxxis.Data/Models/GalaxxisContext.cs:35` | `Server=Wall-E;…;Password=***REMOVED***` (Fallback in `OnConfiguring`) |
| `Galaxxis.Data/Program.cs:10-11` | zwei vollständige Connection-Strings im Doc-Kommentar |

| `Galaxxis.Data/Program.cs:233` | private E-Mail-Adresse des „Nobody"-Kontos |

Gewünschtes Vorgehen (aus der bisherigen Abstimmung): Werte in Konfiguration überführen **und** eine
Template-Datei mit Platzhaltern einchecken, damit eine frische Installation reproduzierbar bleibt —
nicht einfach entfernen und nicht kommentarlos auf Umgebungsvariablen umstellen.

Konkret: `appsettings.Template.json` mit beiden Connection-Strings plus einem Abschnitt für das
Bootstrap-Admin-Konto einchecken, die reale `appsettings.json` in `.gitignore` aufnehmen und
`GalaxxisContext` über DI mit Konfiguration versorgen (siehe C2).

Hinweis: Die Werte bleiben im Git-Verlauf, auch nachdem die Dateien geändert sind. Solange das Repo
privat ist, reicht es, die Passwörter auf dem Server zu wechseln; vor einer Veröffentlichung wäre
ein History-Rewrite nötig.

### B2. `src/Backup/Databases.zip` ist versioniert

960 KB Binär-Dump im Repository. Gleichzeitig ist es aktuell die **einzige** Quelle für das
`GalaxxisIdentity`-Schema — die Identity-Migrationen sind vom Compile ausgeschlossen (siehe C6).
Vor dem Entfernen also erst einen Ersatz schaffen: Schema-Skript nach `dist/db/` legen, analog zu
`create-galaxxis-db.sql`.

### B3. Doppelte Assets

`src/Dummy/assets/images/` und `Galaxxis.Web/wwwroot/images/` enthalten dieselben Dateien
(`galaxy.jpg`, `planet_earth-wallpaper…`, `system.jpg`, `quadrant.jpg`, `cockpit.svg`) — rund 3 MB
doppelt im Verlauf. `src/Dummy` ist ein alter statischer HTML/Vue-Prototyp und nicht Teil der
Solution-Build-Kette.

### B4. `Galaxxis.Web/package.json` ist die Kopie des Dummy-Projekts

```json
"name": "galaxxis-dummy", "description": "ideas and examples", "keywords": ["dummy"]
```

Funktional unkritisch (Gulp-Build läuft), aber irreführend.

## C. Architektur und Wartbarkeit

### C1. Keine Tests, keine CI

Kein Testprojekt in der Solution, keine Pipeline-Datei. Die Spiellogik in `Galaxxis.Core`
(Wachstumsraten, Baukosten, Ressourcenfortschreibung) ist reine Berechnung und wäre gut testbar —
blockiert aktuell nur durch C2.

### C2. `GalaxxisContext` hängt nicht an der DI

Zwei unterschiedliche Strategien koexistieren: `IdentityAppContext` wird per
`services.AddDbContext` registriert, `GalaxxisContext` wird überall direkt mit `new` erzeugt
(`Processor`, sämtliche Provider, `UniverseCreator`) und zieht seinen Connection-String aus dem
hartcodierten `OnConfiguring`-Zweig.

Folgen: keine Testbarkeit ohne echte Datenbank, kein einheitliches Konfigurationsmodell, keine
Kontrolle über Lebensdauer/Pooling. Das ist der Knoten, an dem B1, C1 und C4 gemeinsam hängen —
darum der sinnvollste erste Refactoring-Schritt.

Die Provider sind durchgängig `static` mit optionalem `context`-Parameter. Der Weg von dort zu
injizierbaren Instanzen ist mechanisch, aber breit (7 Provider-Klassen).

### C3. `Processor._actionStore` als statische Liste

`Core/Engine/Processor.cs:44` — handgepflegte Registrierungsliste, deren Vergessen zu einem
stillschweigend ignorierten Event führt (nur `Debug.WriteLine`). Der Code flaggt das selbst:

> *The _actionStore is important! Actions not registered here are not found!
> Change this software architecture to use Dependency Injection instead!*

### C4. Singletons ohne Sperre

`Ticker.Instance` (`Ticker.cs:29`) und `Processor.Instance` (`Processor.cs:84`) sind
Lazy-Singletons ohne `lock` oder `Lazy<T>`. Bei gleichzeitigem Erstzugriff aus zwei Requests können
zwei Instanzen entstehen. Beim `Processor` bedeutet das zwei getrennte `EventQueue`s — eingereihte
Bauaufträge gehen verloren. Die Innereien sind sauber mit `Interlocked` abgesichert, ausgerechnet
die Instanziierung nicht.

### C5. `PlanetCache`: statische, unbegrenzte, nicht threadsichere Caches

`Core/Extensions/PlanetExtensions/PlanetCache.*.cs` hält pro Gebäudetyp ein statisches
`Dictionary<int, TBuilding>`, prozessweit, ohne Eviction und ohne Synchronisierung. Die Einträge
halten `Planet`-Entities aus längst entsorgten DbContexts fest und werden über Requests und Nutzer
hinweg geteilt. Drei Probleme in einem: Speicherwachstum, Race Conditions bei parallelen Zugriffen
und veraltete Spielstände. Der `forceReload`-Parameter ist der Workaround dafür.

**Fix-Richtung:** mindestens `ConcurrentDictionary`, besser ein per-Request-Scope über die DI.

### C6. Identity-Migrationen vom Build ausgeschlossen

`Galaxxis.Web.csproj` enthält `<Compile Remove="Migrations\**" />`. Damit ist `dotnet ef database
update` wirkungslos und der einzige Weg zum Identity-Schema führt über B2. Entweder wieder
aufnehmen oder bewusst durch ein eingechecktes SQL-Skript ersetzen.

### C7. Paketversionen passen nicht zum Zielframework

Alle drei Projekte zielen auf `net8.0`, verwenden aber `Microsoft.EntityFrameworkCore` 6.0.5 und
`Microsoft.AspNetCore.Identity.EntityFrameworkCore` 6.0.24. EF Core 6 ist seit November 2024 aus dem
Support. Upgrade auf 8.x ist bei diesem Nutzungsumfang unkritisch und bringt Sicherheitsfixes mit.

Ebenso am Ende ihres Lebenszyklus: `node-sass` 6 und `gulp` 4 im Frontend-Build.

### C8. `Nullable` in keinem Projekt aktiviert

Die drei `.csproj` setzen kein `<Nullable>enable</Nullable>`. Genau die Klasse von Fehlern, die A4
und A8 ausmachen, würde der Compiler damit anzeigen.

### C9. Exceptions sind `internal` und außerhalb von `Core` nicht fangbar

`Core/Exceptions/UserNotFoundException.cs` deklariert `UserNotFoundException`,
`PlanetNotFoundException` und `EventNotFoundException` ohne Zugriffsmodifizierer — also `internal`.
`Galaxxis.Web` kann sie nicht typisiert fangen. Deshalb steht in `HomeController.Index:59` ein nacktes
`catch`, das jeden Fehler in einen Logout umdeutet.

Nebenbei: Drei Typen in einer Datei mit dem Namen nur eines davon.

### C10. Sync-over-async durchgängig

`HomeController`-Konstruktor: `Task.Run(() => InitializeAsync()).Wait()`. Sämtliche ViewModels:
`GetGalaxxisUserAsync().GetAwaiter().GetResult()`. Funktioniert unter ASP.NET Core, verbraucht aber
unnötig Threadpool-Threads. `ICurrentUserService` hat bereits eine synchrone Variante der
Id-Ermittlung — der Rest könnte durchgehend async werden.

### C11. Zwei UI-Generationen nebeneinander

`HomeController`/`Home.cshtml` ist der ursprüngliche Alles-auf-einer-Seite-Ansatz aus der frühen
Entwicklungsphase, bewusst als sichtbare Gesamtübersicht der Logik gebaut und zum Abbau vorgesehen.
Parallel existieren fünf moderne Gebäude-Controller. `OreMine` ist am weitesten (JSON +
vorgerenderte Partials für AJAX), die anderen vier machen noch PRP-Redirects.

#### Der schnellste Weg durch A1/A2

Der Löschung von `Home` steht genau eine Sache im Weg: **`MageAcademy`, `ElementiumSynthesizer`,
`Shipyard` und `DefenseSystem` haben keinen eigenen Controller** und sind ausschließlich über `Home`
bedienbar. Dasselbe gilt für `Attack` und `Scan` — die Flottenbefehle existieren als
`IAction`-Implementierungen in `Core`, aber `Home` ist ihre einzige Oberfläche.

Daraus ergibt sich eine Reihenfolge, die A1, A2 und C11 zusammen erledigt, statt Code zu härten, der
ohnehin verschwinden soll:

1. **Header-Link und `NewPlayer`-Link entfernen**, `Logout` auf `Start` umstellen (Minuten, macht
   `Home` sofort unsichtbar — schließt die Lücke aber noch nicht, die Routen bleiben erreichbar).
2. **`Home` vorläufig stilllegen** — entweder `[Authorize(Roles = "Admin")]` auf den Controller oder
   ganz aus dem Routing nehmen. Danach ist A1/A2 praktisch entschärft, ohne dass eine Zeile der
   20 Actions angefasst wurde.
3. **Die vier fehlenden Gebäude-Controller nach dem `OreMine`-Muster bauen**, plus eine Oberfläche
   für Flottenbefehle. Das ist die eigentliche Arbeit.
4. **`HomeController`, `HomeViewModel` und `Home.cshtml` löschen.** Damit fallen A1 und A2
   ersatzlos weg.

Schritt 1+2 sind billig und nehmen den Druck von der Sicherheitsfrage; Schritt 3 kann danach in
Ruhe pro Gebäude passieren.

1. **`Home` stilllegen** — Links entfernen, Controller aus dem Routing nehmen bzw. auf die
   Admin-Rolle beschränken (C11, Schritte 1–2). Entschärft A1 und den Großteil von A2 in einem
   kurzen Durchgang, ohne Code zu härten, der ohnehin gelöscht werden soll.

   `Startup.ConfigureServices`) — erledigt A2 für alle übrigen Controller mit einer Zeile.

   absicherbar, was bei einem Spiel mit Balancing-Fragen ohnehin nützlich ist.

   dauerhaft erledigt statt nur repariert.
